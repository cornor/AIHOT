## 2. 部署结构

默认使用 Docker Compose，项目目录暂定 `/opt/gamehot`，统一使用北京时间。

| 服务 | 作用 | 网络范围 |
|---|---|---|
| Caddy，或服务器现有反向代理 | HTTPS、证书续期、域名入口 | 对外 80、443 |
| web | 网站页面 | 容器内部；需要时绑定宿主机回环地址 |
| api | 页面数据、公开 API、RSS、管理员后台 | 容器内部 |
| worker | DeepSeek 分析、事件归组、日报等任务 | 容器内部 |
| PostgreSQL 17 | 文章、分析、任务和运营数据 | 容器内部 |
| WeRSS | 微信读书采集、公众号 RSS | 内部端口 8001；经域名 `/werss/` 提供受保护的管理入口，宿主机端口仅绑定回环地址 |
| collector | 定期触发 WeRSS 采集，再运行 RSS 入库脚本 | 与 WeRSS 共享容器网络命名空间 |
| setup | 数据库迁移、主题初始化 | 一次性任务 |

collector 与 WeRSS 共享网络命名空间，使现有入库脚本继续访问 `127.0.0.1:8001`；它们同时连接站点内部网络，collector 可访问 PostgreSQL。不会为采集开放通用内网访问权限。

若服务器已有 Nginx、Caddy 或其他站点，优先复用现有入口，仅增加本域名配置。具体端口、磁盘路径和镜像构建位置在服务器检查后确定。

### WeRSS 子路径与访问控制

- `/werss` 跳转到 `/werss/`；该前缀下的请求先验证游戏研发情报的管理员会话，再转发到 WeRSS，转发时移除 `/werss` 前缀。网站其他路径继续走原有 web 服务。
- 复用站点已有的 `/api/auth/check`：有效管理员会话返回 204，否则返回 401。Caddy 使用 `forward_auth`，现有 Nginx 则使用 `auth_request`。校验依据是会话 Cookie，保留 WeRSS 自己的 Bearer 请求头。
- 未登录的页面访问转到站点登录页，登录后返回 `/werss/`；接口请求未登录时返回 401。现有登录返回地址仅允许 `/admin`，部署版本需增加对 `/werss` 路径的严格校验，禁止外部跳转、协议相对地址和非法路径。
- 保留 WeRSS 自身的管理员登录。因此首次使用可能先登录站点，再登录 WeRSS；不在本次部署中合并两套账号。
- 整个 `/werss/` 前缀均受保护，包括原生 RSS、文章正文、静态文件、下载和 WebSocket。管理响应禁止缓存，并设置禁止搜索引擎收录的响应头；网站公开 RSS 仍只提供已允许公开的内容。
- 已查看本机 WeRSS 源码：前端构建基础路径目前固定为 `/`，部分链接也使用根路径。执行时先核对与固定运行镜像对应的源码，再构建支持 `/werss/` 的前端，统一路由、API、资源、二维码、下载及 WebSocket 地址。只改 RSS 地址或增加代理规则不足以完成适配。
- WeRSS 生成的管理链接使用正式域名及子路径；collector 仍通过内部 `127.0.0.1:8001` 采集，不受浏览器入口登录影响。

## 3. 执行步骤

### 第一步：检查服务器和域名

确认计划后，先做只读检查：

1. 验证 SSH 登录；若需要密码或额外认证，再由使用者完成认证。
2. 检查 Linux 发行版、CPU 架构、内存、磁盘、Docker/Compose 和已有服务。
3. 检查 80、443 端口占用、现有代理、防火墙和相关云平台接入配置。
4. 检查 `gamehot.paoyou.com` 的 DNS 记录是否指向 `114.132.169.89`，以及是否有不匹配的 AAAA 记录。
5. 根据资源和架构验证应用与 WeRSS 镜像可用性。资源较少时，考虑在本机构建匹配服务器架构的 Linux 镜像后传送。

预期产物：服务器检查结果、确定的部署目录和入口配置。存在冲突时先给出具体处理方案，涉及覆盖其他业务或额外费用的操作另行说明。

### 第二步：准备可复现的部署版本

1. 将尚未提交的技术精选新标准纳入部署版本。
2. 将目前放在本机 `.data/` 中的必要采集运行代码、WeRSS 配置模板和兼容补丁整理到可版本管理的部署目录；保留补丁来源和许可证信息。
3. 把 `/opt/homebrew/bin/node` 等 Mac 路径改成容器内可用路径，增加 collector 的 Python 运行环境。
4. 将 11 个账号的非敏感订阅清单保存为可复现配置；密码、授权 Cookie、运行数据库仍作为私有数据保存。
5. 准备 Compose 部署配置、健康检查、日志轮转和自动重启；保留 worker 的正常退出等待时间，避免中断已付费请求。
6. 完成 WeRSS 的 `/werss/` 前端适配、代理访问控制和站点登录返回地址支持；验证登录校验及非法返回地址拒绝行为。
7. 运行类型检查、独立空库后端测试、网页构建与测试；测试使用本地模型桩和测试密钥。
8. 检查提交不含密钥、`.env` 或 `.data/`，推送到自己的 fork，并记录服务器将使用的固定提交。

服务器取代码可使用公开仓库的 HTTPS 地址、只读部署凭据，或由本机通过 SSH 传送固定提交的代码包。无需把本机 GitHub SSH 私钥复制到服务器。

本次沿用当前已运行的定制版本，不直接部署 fork 的 `main`。该分支包含本地尚未适配的新版框架更新，需要单独处理升级。

### 第三步：安装和配置服务

1. 创建部署目录；按检查结果安装必要运行组件，获取应用和 WeRSS 镜像。
2. 配置 `SITE_URL=http://gamehot.paoyou.com`、`SITE_DOMAIN=gamehot.paoyou.com` 和正确的反向代理设置。
3. 生成服务器专用的数据库密码、管理员密码和会话密钥。通过 SSH 安全传送现有 DeepSeek Key，不写入计划、Git 或公开日志。
4. 网站前端只配置网站地址与 API 连接；模型密钥仅供必要的后端进程使用。
5. 私有配置文件权限设为 `600`，为数据库、文件、WeRSS 数据和证书配置持久化存储。
6. 初次启动保持采集和模型调用关闭，先验证数据库、网页与 API。飞书和 IndexNow 保持关闭。

### 第四步：迁移本机数据

1. 确认源、目标代码与数据库迁移版本兼容，记录本机文章、信源、精选及回执数量。
2. 暂停本机 worker 和 collector，等待正在进行的采集与付费请求结束；本机网页可继续读取已有数据。
3. 导出 PostgreSQL 一致性备份；使用 SQLite 备份机制或在 WeRSS 停稳后备份其数据库。整理必要上传文件和订阅配置。
4. 在服务器空数据库中恢复数据，应用增量迁移，再初始化主题；恢复后保留用户配置和已取消的模型次数限制。
5. 核对迁移前后数量，确认没有重复文章、丢失摘要或重新计费；不复制本机临时日志、旧测试数据库和无关缓存。

微信读书授权不作为可保证迁移的登录状态。服务器使用新的授权流程，避免将本机有效 Cookie 当作服务器可长期使用的凭据。

### 第五步：接通服务器上的公众号采集

1. 在服务器启动 WeRSS，配置相同的 11 个账号。
2. 配置域名、HTTPS 及受保护的 `/werss/` 入口，由使用者通过 `http://gamehot.paoyou.com/werss/weread` 完成微信读书扫码授权。域名暂不可用时才使用 SSH 隧道作为临时入口。
3. 验证真实文章列表及正文获取，随后验证 RSS 入库和去重；仅能读取账号封面不算采集成功。
4. 启用服务器 collector 和 worker，采集周期之间等待 30 分钟；单个账号失败不阻塞其他账号。
5. 确认 DeepSeek 请求仍经过正常回执机制，新文章能筛选、写摘要并发布。
6. 对正文失败和登录失效记录明确错误；登录失效需要再次扫码，不承诺永久免扫码。

服务器接管后，本机 worker 和 collector 保持暂停，作为回退环境保存，避免两边重复采集和付费处理。

### 第六步：域名、HTTPS 和内部上线

1. DNS 和服务器入口就绪后，配置域名反向代理及 HTTPS 证书续期。
2. 在反向代理中为整站启用管理员会话校验，仅放行登录流程及必要的登录页面资源。使用者明确内部使用，无需公开文案确认。
3. 验证 HTTP 到 HTTPS 跳转、首页、全部资讯、精选、搜索、日报、后台登录、RSS、公开 API 和 MCP。
4. 检查 RSS、分享链接、站点地图和页面中的绝对地址都使用正式域名。
5. 确认数据库、API 内部端口和 WeRSS 管理端口没有直接暴露公网；未经登录不能读取资讯或数据接口。
6. 验证 `/werss/` 页面导航、子页面直接打开与刷新、二维码、资源加载、API、下载和 WebSocket；匿名访问管理页及原生 RSS、正文均不能取得内容，登录失效后重新验证会话。

## 5. 备份与回退

- 部署前保存本机数据库、必要文件、WeRSS 数据和固定代码版本。
- 服务器每天备份 PostgreSQL、WeRSS SQLite 及必要文件到私有目录，初定保留 7 份；配置日志轮转，检查磁盘占用。
- 默认先使用服务器本地备份，不购买额外服务。本地备份不能覆盖整机或磁盘丢失，外部备份可另行配置。
- 代码更新前先备份，再构建、停稳 worker、迁移和启动；不删除数据卷。
- 失败时停用服务器采集和模型调用，保留现场与日志；按固定版本和备份恢复。本机可恢复处理，但先确认只有一端运行。
- 记录 DNS 切换前状态；如迁移中途已有服务器新数据，回退前先保存，避免丢失。

- 自动启动、异常重启、定期采集、日志轮转和备份任务已配置，并验证备份可读取和恢复。
